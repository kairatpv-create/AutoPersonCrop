## D01–D02: отказ от выбора целого снимка по времени

Ранее первый обмен и двусторонние изменения выбирали целую локальную/облачную копию по максимальной дате. `dueAt` и `triggerAt` участвовали в «свежести». Ответ PUT 409 немедленно заменял локальную базу удалённой копией.

Теперь:

- Сохраняется общий подтверждённый снимок v7, его SHA-256 и серверная ревизия. Нормализация не зависит от порядка полей/строк и записи числа `1`/`1.0`.
- Сравнение выполняется по трём версиям каждой записи: общая, локальная, облачная. Независимые добавления/правки и односторонние удаления объединяются. Дата выполнения проекта/напоминания не определяет приоритет; максимальной даты в алгоритме больше нет.
- Конкурирующие изменения одной записи, удаление против правки и столкновения новых числовых ID останавливают обмен. Проверяются зависимости объединённого результата. Отсутствие общей версии при двух разных непустых копиях также требует остановки.
- Оба валидных конфликтующих снимка сохраняются с контрольными суммами в `noBackupFilesDir/sync-conflicts`, одинаковая пара не дублируется каждые 30 секунд. Настройки позволяют экспортировать локальную резервную копию с файлами и сохранённую облачную копию конфликта без файлов.
- 409 приводит к повторному GET и повторному объединению с тем же общим снимком, максимум три попытки. Облачная копия не применяется как ответ на 409.
- Один координатор последовательно выполняет вход, выход, удаление и обмен; локальная правка за время сети повторно проверяется внутри SQLite writer transaction до удаления первой строки.
- Перед применением облачной версии создаётся проверенная нативная страховочная копия D14. Сбой её записи отменяет замену. Проверяется поколение записи, к которой относятся локальные вложения; удаление/смена поколения останавливаются, файлы остаются на месте.
- Облачный экспорт сразу формирует компактный JSON, чтобы отступы локального backup не уменьшали доступный серверный лимит; отдельный тест использует 8000 искусственных заметок. Ручной JSON-экспорт сохраняет прежнее форматирование. Облачный экспорт исключает настройки и бинарные вложения; он больше не кодирует все файлы в Base64 для последующего удаления из JSON (улучшение D13).

**Ограничение:** это безопасный обмен с явными конфликтами, без миграции старых ID в UUID и без нового протокола сервера. Нет автоматического решения столкновений числовых ID или выбора между двумя разными правками одной записи. Сначала экспортировать обе копии; ручное объединение требует отдельного проверяемого действия. Молчаливого «победителя» нет. Сложные конфликты не объявлены автоматически разрешёнными.

Если приложение переустановлено или не имеет новой общей версии, одинаковые копии устанавливают общий снимок, пустое устройство получает облачные данные, а пустой сервер получает локальные. Разные непустые копии сохраняются до разрешения конфликта. Повреждённый внутренний файл состояния не считается «новым устройством».

## D03: привязка к аккаунту

Сервер подтверждает токен через существующий `/api/account`; только после этого JWT subject используется как стабильный идентификатор владельца. Email сравнивается с подтверждённым сервером значением. `syncUid="account"` заменён реальным идентификатором.

Владелец и общий снимок записываются атомарно отдельно от обычных UI-настроек и сохраняются после выхода. Другая учётная запись не получает эту базу. Для обновления со старого приложения используется сохранённый `sync_email`: старый выход его не удалял. Повторная регистрация того же email после удаления создаёт новый subject и также не получает старую базу автоматически.

Переключение одного набора локальных данных на другого владельца отклоняется без очистки базы/файлов. Отдельные локальные профили для нескольких аккаунтов не реализованы. Нельзя восстановить историю владельца, если пользователь уже переключился/передал данные старой небезопасной версией до обновления.

## Серверная гонка первой записи

Исправление клиента не может устранить гонку старого сервера: `SELECT ... FOR UPDATE` по ещё не существующей строке sync ничего не блокировал. В подготовленном сервере PUT сначала блокирует строку владельца, затем проверяет ревизию и записывает снимок. Две первые записи с baseRev=0 дают один успех и один 409. Удаление аккаунта берёт ту же блокировку.

Серверный исходник скопирован из точного web-коммита `3a28807ee98aa657b90bba5a35c776ead8c2145f`; web-интерфейс не разрабатывался. Добавлены валидация полного v7 и запрет импорта settings/attachments через sync. Принимаются совместимые снимки актуальных Android/static-web экспортёров. Идентификаторы/времена сервер проверяет в диапазоне JS safe integer; значения вне него отклоняются с сохранением предыдущего снимка.

**Развёртывания не было.** Старые установленные клиенты всё ещё могут выбирать снимок небезопасным способом. Общую production-защиту нельзя считать завершённой до согласованного выката сервера и обновления клиентов. Исходная web-ветка с autoDeploy не изменена.
