# D14 — восстановление после аварийного завершения процесса

Основа: D06, коммит `8aac1b82ae9d391fcfd169c4b9c3e5ca22fd5f70`.
Ветка: `organizer-d14-restore-recovery-20261022`.

Это часть D14 о согласовании базы и вложений после сбоя. Ограничение полного
размера/распаковки JSON/ZIP и отдельная долговременная страховочная копия
базы перед импортом остаются открытыми. Весь D14 закрытым не объявляется.

## Изменение поведения

До этого изменения завершение процесса между установкой новых файлов и
SQL commit оставляло старые записи с новыми вложениями. Сценарий воспроизведён
на неизменённых исходниках D06 отдельным JVM-процессом с `Runtime.halt(73)`.

Теперь перед заменой публикуется журнал `files/organizer-restore.json`.
Новые файлы, индекс и маркер поколения подготовлены отдельно; старый каталог
сохраняется в `attachments-restore-*/previous`. Идентификатор восстановления
записывается в SQLite в той же транзакции, что и все восемь коллекций.

При следующем открытии базы/хранилища решение принимается по SQLite:

- Транзакция не зафиксирована: вернуть прежний каталог, сохранить прежние
  записи и настройки, убрать подготовленные файлы после успешного возврата.
- Транзакция зафиксирована: проверить новое поколение, индекс и наличие/размеры
  файлов, закончить восстановление экспортированных настроек, затем очистить
  резервный каталог и журнал.
- Решение нельзя безопасно подтвердить: сохранить файлы и остановить открытие
  приложения с понятной ошибкой RU/EN и действиями «Повторить»/«Закрыть».
  Неполное состояние не открывается как обычная пустая база.

Для прямого восстановления только вложений точкой фиксации служит установка
нового поколения файлов; SQLite в этом режиме не заменяется.

Добавлена внутренняя таблица `backup_restore_state`, содержащая один токен.
Версия базы остаётся 9; таблицы пользовательских данных не пересоздаются.
Проверен запуск на копии искусственной базы схемы 9 без этой новой таблицы.
Ранние миграции и обычные операции редактирования не переписывались.

Журнал и новые файлы синхронизируются, затем синхронизируются каталоги.
Удаление служебного дерева не следует символическим ссылкам. После переноса
настроек публикуется отдельная запись завершения: повторная очистка не должна
заново применять настройки из старой копии поверх последующих правок.
PIN, учётная запись, токены и служебные показатели синхронизации не переносятся.

Если `endTransaction()` завершился исключением, код не предполагает исход SQL:
помощник закрывается, каталог и журнал сохраняются. Следующее открытие
сверяет фактическую фиксацию SQLite и выбирает согласованный набор файлов.
Если очистка завершённого восстановления не удалась, успех остаётся успехом;
очистка повторяется при открытии. Нераспознанные подготовительные каталоги
без `previous` сохраняются; каталог с прежними файлами без журнала блокирует
автоматическое решение, а не удаляется.

Форматы экспорта JSON/ZIP и облачного снимка 7 не меняются. Снимок без
`attachments` не заменяет локальные файлы. Алгоритм синхронизации, Render,
iOS, версия приложения и подпись не менялись. Обычный интерфейс сохранён;
добавлен только экран ошибки, необходимый при небезопасном восстановлении.

## Воспроизведение проверок

Пройдено 452/452 целевых сценария: 68 восстановления, 1 регрессионный сценарий
с отдельным аварийным процессом, D04 — 235, D05 — 67, D06 — 64+17.
Восстановление проверено с SQLite DELETE и WAL: остановка подготовки, обоих
переименований, до/после SQL commit, во время очистки и повторного восстановления.
Включены пустая полная копия, последовательные импорты, неясный исход commit,
небезопасный журнал/ссылки, ошибки записи настроек и синхронизации каталогов.
На D06 тот же регрессионный сценарий ожидаемо не проходит (0/1), поскольку
после аварии старые записи связаны с новыми файлами.

```sh
python tools/audit/run_jvm_audit.py --source mobile/android \
  --jars /path/to/supplied-jars --output /path/to/d14-recovery \
  --suite restore-recovery
python tools/audit/run_jvm_audit.py --source mobile/android \
  --jars /path/to/supplied-jars --output /path/to/d14-probe \
  --suite restore-recovery-probe
```

Набор `restore-recovery-probe` также запускается с исходниками D06 как
негативный контроль: ожидается отказ проверки согласованности старой базы
и вложений после принудительного завершения.

Результаты и SHA-256 исполнявшихся исходников сохранены в
`evidence/d14-restore-recovery.json`. Полный аудит повторно не проводился.

## Границы проверки

Проверки выполняются на искусственных записях, файлах, PIN и токенах через
настоящие Kotlin-код, SQLite JDBC и файловую систему Linux. После аварии
запускается новый JVM, без выполнения `finally` аварийного процесса.
Реальные пользовательские данные и сервисы не используются.

Android SQLiteOpenHelper, жизненный цикл Activity, диалог ошибки и поведение
накопителя телефона этими тестами не подтверждены. Физическое отключение
питания не проверялось. Проверки индекса и размеров не являются контролем
целостности каждого байта при произвольном повреждении накопителя.

Перед выпуском нужны инструментальные проверки на Android: остановка процесса
во время импорта, повторное открытие, отказ записи при нехватке места,
поведение диалога ошибки и повторный импорт. Только тестовые данные и отдельная
установка; установленная пользовательская версия этим этапом не заменяется.

После успешных целевых тестов выполняется одна `assembleDebug` через
существующий workflow. Выгрузка установочного APK для этой ветки отключена.
