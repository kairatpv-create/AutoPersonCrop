# D06 — безопасное восстановление вложений

Основа: результат D05, коммит
`11ca2fc050c84f6ed0b8e0d3920642bdf3f27ee7`.
Ветка: `organizer-d06-attachment-restore-20261021`.

## Изменения

Проверка всех вложений выполняется до записи: обязательные поля и типы,
уникальные ID и имена файлов, Base64 и размер декодированного файла.
`storedName` должен быть одним непустым именем, без переходов по каталогам,
разделителей путей, двоеточий и управляющих символов. Копия не может записать
данные через `../`, абсолютный путь или перезаписать другой файл тем же именем.
Та же проверка применяется при прямом вызове `AttachmentStore.restoreBackup`.

Новые файлы и индекс сначала полностью записываются в отдельный временный
каталог рядом с текущим хранилищем; файловые потоки синхронизируются через
`FileDescriptor.sync`. Старые файлы на этом этапе не изменяются. При ошибке
подготовки база ещё не заменяется.

После успешной подготовки `replaceAll` выполняет SQL в транзакции. Перед её
фиксацией старый каталог перемещается в резервный, новый — на его место.
Ошибка переименования вызывает откат SQL и возврат старого каталога. Резервная
копия удаляется только после возвращения из завершённой транзакции.
Операции чтения/изменения хранилища синхронизированы: экспорт не создаёт пустой
каталог в промежутке между переименованиями и не читает частичный индекс.

Ошибки записи больше не подавляются. Ошибка очистки после успешной фиксации
не превращает успешное восстановление в отказ; остаётся резервный каталог.
Если повторная ошибка мешает вернуть старый каталог, его файлы сохраняются
в `attachments-restore-*/previous`, очистка отключается, а сообщение явно
говорит о сохранённом каталоге для восстановления. Успех не сообщается.

Облачный v7 без `attachments` сохраняет прежнее поведение: локальные файлы
не заменяются и временный каталог не создаётся. Формат экспорта не менялся.

## Проверки

- 64/64 теста структуры и совместимости: небезопасные имена, повреждённые
  данные и метаданные, совпадающие имена с разными ID, полный и прямой импорт,
  JSON/ZIP, старые схемы 3–5, бинарные/русские/пустые файлы, пустой массив,
  облачный снимок 7. Отдельно проверен настоящий отказ файловой системы
  при слишком длинном имени.
- 17/17 тестов записи и возврата состояния: создание каталога/отказ доступа,
  создание подкаталогов, запись каждого файла и индекса, частичная запись,
  оба переименования, исключение после установки файлов до SQL commit,
  ошибка очистки после успеха, повторный сбой отката и параллельный экспорт.
- После обычных отказов сравниваются все записи/настройки, SHA-256 SQLite,
  файлов, индекса и контрольных файлов вне `data`; временные каталоги удалены.
  После искусственных сбоев успешный повторный импорт проверен отдельно.
  При двойном сбое проверены неизменность SQLite и сохранность всех старых
  файлов в резервном каталоге, затем восстановлена только тестовая фикстура.
- D04: 235/235; D05: 67/67. Результаты прежних наборов совпали с сохранёнными
  отчётами. Всего 383 успешно выполненных целевых сценария.
- Негативный контроль на D05: 49 из 64 проверок нового набора ожидаемо не
  проходят; предыдущая реализация принимает небезопасные вложения. 15 других
  сценариев проходят. Каждый отрицательный сценарий имеет отдельную фикстуру.

Результаты и SHA-256 исполнявшихся исходников:
`evidence/d06-attachment-restore.json`.

Команды запуска из корня репозитория:

```sh
python tools/audit/run_jvm_audit.py --source mobile/android \
  --jars /path/to/supplied-jars --output /path/to/d06-validation \
  --suite attachment-validation
python tools/audit/run_jvm_audit.py --source mobile/android \
  --jars /path/to/supplied-jars --output /path/to/d06-restore \
  --suite attachment-restore
```

Исполняется настоящий Kotlin-код с SQLite JDBC и файловой системой во временных
каталогах. Сбои ввода-вывода внедряются только тестовым адаптером; проверки на
телефоне, принудительного завершения процесса или отключения питания не было.
Долговечный журнал восстановления после аварии и автоматический возврат
резервного каталога после повторного сбоя остаются задачей D14. Совместная
атомарность SQLite/файлов при потере питания этим изменением не объявляется.

После тестов — одна проверочная компиляция `assembleDebug` через существующий
workflow без выгрузки APK. Версия, подпись, схема базы, интерфейс, алгоритм
синхронизации, Render и iOS не менялись. Повторный аудит не проводился.
