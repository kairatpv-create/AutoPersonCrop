# D05 — отказ от частичного восстановления

Основа: результат D04, коммит
`54ce800e35565843ffe666f1ef6804f23bcde3e6`.
Рабочая ветка: `organizer-d05-restore-integrity-20261021`.

## Изменения

Проверка копии отклоняет повторяющиеся идентификаторы внутри каждого раздела
до записи в базу или файлы. Для связей проекта с заметкой проверяется пара
`projectId`/`noteId`, для остальных записей — `id`, включая индекс вложений.
Одинаковые ID в разных разделах допустимы; разные связи одного проекта или
одной заметки тоже допустимы. Нет выбора первой/последней конфликтующей записи
или молчаливого удаления дубликатов. Ошибка содержит раздел и пояснение RU/EN.

Все восемь вставок в `NoteDatabase.replaceAll` используют `insertOrThrow`;
подавление конфликтов при импорте связей удалено. Любая ошибка вставки выходит
из метода до отметки успешной транзакции. SQLite откатывает прежние удаления
и вставки вместе. Восстановление вложений после ошибки базы не запускается.
Защита работает и при прямом вызове `replaceAll` в обход JSON-проверки.

## Проверки

- 67/67 сценариев D05: одинаковые и конфликтующие дубликаты по разделам,
  составной ключ связей, эквивалентные целочисленные ID, ZIP и облачная версия 7,
  SQL-ошибка на первой/второй вставке каждой таблицы, SQL-ошибка удаления каждой
  таблицы, прямой вызов замены с дубликатами и успешное полное восстановление.
- После каждого отказа проверены экспорт всех записей/настроек и SHA-256
  SQLite, файлов вложений и индекса. Входящие ID повышены на 1000, чтобы
  проверять также сохранение счётчиков AUTOINCREMENT при откате.
- После каждого искусственного SQL-сбоя снят тестовый триггер и успешно
  повторено полное восстановление; база не остаётся в незавершённой транзакции.
- Регрессия D04: 235/235 прежних целевых сценариев прошли на новом коде;
  результаты совпали с сохранённым отчётом D04.
- Негативный контроль на исходной основе D04: новый набор обнаружил дефект —
  58 ожидаемых отказов проверок, 9 прошедших сценариев. Исходный код принимает
  дубликаты и подавляет ошибки вставки.

Результаты и хеши исполнявшихся исходников:
`evidence/d05-restore-integrity.json`.

Команды запуска из корня репозитория:

```sh
python tools/audit/run_jvm_audit.py --source mobile/android \
  --jars /path/to/supplied-jars --output /path/to/d05-results \
  --suite restore-integrity
python tools/audit/run_jvm_audit.py --source mobile/android \
  --jars /path/to/supplied-jars --output /path/to/d04-regression \
  --suite backup-validation
```

Это хостовые проверки настоящего Kotlin-кода с SQLite JDBC и адаптерами
Android, без реальных данных и обращений к серверу. Сбои создаются настоящими
SQL-триггерами `RAISE(ABORT)`, а не подменой результата метода приложения.
Проверка на телефоне не выполнялась. Дисковые сбои при последующей записи
вложений и совместная атомарность базы/файлов остаются отдельными задачами D06/D14.

После тестов предусмотрена одна компиляция Android `assembleDebug` в GitHub
Actions без выгрузки APK-артефакта. Схема базы, версия, подпись, интерфейс,
алгоритм синхронизации, Render и iOS не менялись. Повторный аудит не проводился.
